# Corpus provenance — production vs `corpus/`

**Status:** open finding, 2026-08-19. Nothing has been changed. This document records a
divergence discovered while preparing the phase 1d honesty baseline, and it is the input
to a decision only the corpus authors can make.

Register entry: **C-10**. Related: C-1, C-1b, G-1, G-8, K-2, K-3.

---

## The short version

The corpus this benchmark grades against is **not the corpus the team authored.** The local
copy has been through at least three unrecorded transformations, and the two have silently
forked. Neither side is wholly authoritative:

| | production (`/api/nodes`) | local `corpus/` |
|---|---|---|
| role | the authoring surface — where the team writes | what every recorded run was scored against |
| nodes / emails | 25 / 184 | 15 / 167 |
| `match` keywords | **absent entirely** | present on 96 emails, 114 op sets |
| date grammar | **pre-migration** — still carries `@11:00-11:30` | migrated to day-level |
| prose | has typos (`"there going to make"`) | copy-edited (`"they are going to make"`) |
| `tier` labels | absent (all `null`) | present on all 167 |
| abandoned drafts | 6 empty `node-N` scaffolds, 2 stubs, 1 superseded node | none |

**Production is older, not newer.** That is the single most counter-intuitive fact here and
the reason this cannot be resolved by pulling production down over the top.

---

## How this was found

Checked with a read-only `GET https://secretarybench.vercel.app/api/nodes` on 2026-08-19,
with the corpus owner's explicit authorisation. Response saved outside the repo; `corpus/`
was not touched. `GET` cannot mutate — the write verbs are `POST` on `/api/nodes` and
`PUT`/`DELETE` on `/api/nodes/[id]`, none of which were called.

> **Do not use `scripts/recover_corpus.py` to repeat this check.** It performs the same
> `GET` and then unlinks and rewrites `corpus/nodes/*.json` in place, which would destroy
> the lever provenance of every recorded run (C-1) and erase the local-only work catalogued
> below.

## 2. `match` does not exist in the authored corpus

This is the important one. A production answer key looks like this:

```json
{"create": "Create A List For Athlete Visit", "kind": "todo", "on": {"by": "@athlete_visit"}}
```

There is no `match` field. The local copy has `"match": ["athlete"]` added.

That field was generated by **`scripts/fix_match.py`**, which states its own purpose:
*"Give each obligation a model-robust `match` keyword set derived from the op NAME."*
It has been applied to **96 emails / 114 op sets**.

### What this re-attributes

`match` is what the grader uses to decide whether the model's object is the obligation
(`grader.py:68`). Register finding **G-1** — that the grader demands a keyword appearing
nowhere in the mail the model reads, measured at **76%** of the dominant failure bucket — is
therefore **caused by a locally-run generation script, not by the team's authoring.**
`["athlete"]` was extracted from "Create A List For Athlete Visit"; `["location"]` from
"Contact Retreat Location".

### But the script was solving a real problem

Measured offline against `captures/baseline-sonnet-4-5`, holding everything constant except
the identity policy:

| identity policy | emails | ops |
|---|---|---|
| null model, no tool calls at all (V-3 floor) | 64/167 · 38% | — |
| **authored keys, shipped grader** | **67/167 · 40%** | 73/190 · 38% |
| `fix_match.py` keywords — what every run used | 97/167 · 58% | 110/190 · 58% |
| **authored keys + match any content word** | **99/167 · 59%** | 109/190 · 57% |
| `fix_match.py` keys + any content word | 96/167 · 57% | 108/190 · 57% |
| oracle titling by the key itself (ceiling) | 167/167 · 100% | — |

Reproduce: `python -m sb.regrade captures/baseline-sonnet-4-5 --corpus <variant>`.

**On the authored corpus with the shipped grader, a real model scores 67/167 — three points
above the do-nothing floor.** Without generated keywords the benchmark measures essentially
nothing, because `schema.py:155` falls back to `match = [name]`, requiring the entire
obligation name as one contiguous substring. `fix_match.py` rescued a benchmark that was
otherwise inert. It is not vandalism.

### The finding that matters for phase 2

**Matching any content word from the authored op name scores 99/167 — equal to or slightly
better than the generated keywords, with no corpus mutation at all.**

The 99-vs-97 gap is two emails and inside noise, so the claim is *"as good as"*, not
*"better than"*. But it means the entire keyword-generation step may be unnecessary: the
same result is available by changing the **grader's matching rule** and leaving the corpus
exactly as authored. That would let production stay the single source of truth and remove
the largest cause of local divergence.

Stated limit: measured on one run of one model. It should be re-checked against a second
captured run before being treated as settled.

## 3. Date expressions differ on 36 ops

`fix_match.py` promises *"Only `match` changes — never op name/kind/date."* Something else
changed dates. Most look like a deliberate schema migration that never reached production —
commit `dc5d762` (2026-06-01) is titled *"Day-level grammar: drop time-of-day and duration"*,
and production still carries the old form:

| email | production | local |
|---|---|---|
| `Day-of-execution_and_Aftermath.launch-livestream` | `{"eq": "dom:10,+2m @19:00-20:00"}` | `{"eq": "dom:10,+2m"}` |
| `Enterprise_Ai_Selection.ai-meeting-schedule` | `{"eq": "next:TUE @10:00-11:00"}` | `{"eq": "next:TUE"}` |

But a few are **semantic answer changes**, not migration:

| email | production | local | effect |
|---|---|---|---|
| `Company-Retreat.inquiry-on-vip-list` | `{"by": "@retreat_date"}` | `{"by": "serve+1d"}` | different deadline entirely |
| `Company-Retreat.planning-call-and-forms-…` | `{"by": "dom:21,0m"}` | `{"eq": "dom:21,0m"}` | deadline → exact day |
| `Company-Retreat.in-town-and-would-love-…` | `{!athlete_visit = dom:22,`**`0m`**`}` | `{!athlete_visit = dom:22,`**`1m`**`}` | anchor moved one month |

That last one is the case a human hand-grader hit first and correctly flagged as incoherent:
the email prose says *"August 22nd"*, production's anchor resolves to June 22, and local's to
July 22. **All three disagree.** Whoever shifted `0m` → `1m` moved it closer to the prose
without reaching it. Register **K-3**.

Also: `depends_on` differs on 4 emails, and 46 bodies carry local copy-edits.

## 4. None of this is in git

The entire 167-email corpus arrived in a **single commit** (`24331fb`, 2026-07-26) titled
`.`, alongside a rewrite of the harness. Before it, `corpus/` had been reset to empty and
previously held 13 prototype emails. There is no commit adding a node, fixing an email, or
running `fix_match.py`.

Searched all 157 commits across every ref including `origin/backups`: the 176-email corpus
that `past/claude-sonnet-4-5.md` was scored against **exists nowhere in git.** It lived only
in production and has since been edited there.

So the local transformations — keyword generation, grammar migration, copy-edits, tier
labelling — have no recorded history, no author, and no date. They are only visible by
diffing against production, which is what this document is.

---

## Resolution — measured 2026-08-19, after the first draft of this document

**The first draft framed production as the authoring source that local had diverged from.
That framing is wrong, and the evidence reverses it.**

Classifying all 46 body differences:

| classification | count |
|---|---|
| `local` = `production` minus time-of-day (the `dc5d762` migration) | 40 |
| differs only inside a `{token}` | 1 |
| prose wording differs | 5 |
| **emails where production holds text or a correction local lacks** | **0** |

Of the 5 prose differences, local holds the typo correction and production holds none.
**Production has not moved forward since the snapshot.** Every difference is accounted for by
a transformation applied locally.

And the residue that is *not* the grammar migration is a coherent **authoring pass**, not
damage:

| kind of edit | count | examples |
|---|---|---|
| answer keys tightened | 9 | `by`→`eq` (deadline → exact day) ×3, `@Review_Meeting`→`next:FRI`, `any_of`→`eq`, `@board_signoff-1d`→`dom:14,0m` |
| retrieval spans lengthened | 3 | `@Delayed_Release_Date+5d`→`+5w`, `+9d`→`+6w` |
| prose converted to tokens | 2 | `"possibly a day earlier?"`→`"by tomorrow, {+1d}?"`, `"before {this:THU}"`→`"by {+1d}"` |
| `depends_on` types corrected | 4 | `type: date` → `type: static` |

Someone was deliberately improving this corpus: making vague deadlines checkable, replacing
anchors with concrete expressions, lengthening spans. **That work exists only in `corpus/`.**

### The corrected picture

- **`corpus/` holds the authoritative content.** It is production plus a schema migration plus
  a genuine authoring pass.
- **Production is a stale backup** that predates all of it.
- **`match` remains the one exception.** It is machine-generated from op names, it is the root
  cause of G-1, and §2 shows the grader scores as well without it.

**The risk is therefore the reverse of what the first draft implied.** `recover_corpus.py`
would not restore truth; it would overwrite a real authoring pass with a stale snapshot. The
hazard box in the register is correct, for a stronger reason than was known when it was
written.

### One incomplete edit, worth naming

In `Company-Retreat.in-town-and-would-love-to-connect`, a single edit changed the prose
**June → August** *and* the anchor `dom:22,0m` → `dom:22,1m`. But `1m` from a June-28 serve
resolves to **July 22**, not August. The edit was made and left half-finished, which is why
the email says August, the answer key says July, and a hand-grader flagged it as incoherent
on first contact. Register **K-3**.

## The decision this needs

Not a decision for the repair work to take unilaterally. It belongs to whoever owns the
authored corpus.

1. ~~**Which side is authoritative?**~~ **Answered by the resolution above: `corpus/` is.**
   What remains is a single yes/no for the corpus authors: *did someone perform an authoring
   pass around July 2026 — tightening answer keys, lengthening spans, converting prose to
   tokens — that was never pushed back to the webapp?* If yes, local is simply ahead and the
   repair proceeds on it. If nobody recognises that work, its provenance needs explaining
   before anything is built on it.
2. **Should `match` exist at all?** §2 suggests it need not: a better grader-side matching
   rule scores the same with the corpus left as authored. That would end the divergence at
   its largest source.
3. **Is `rebrand-execution` real?** Six emails, four graded, never benchmarked.
4. **Should the migration be written back to production**, so the authoring surface and the
   benchmark stop forking?
5. **Should the abandoned `node-N` scaffolds be deleted upstream**, so a future pull is clean?

Until 1 and 2 are answered, every score in this repository is provisional in a way the
register did not previously capture: it is measured against answer keys that were partly
machine-generated, from a snapshot that has silently diverged from its source.
