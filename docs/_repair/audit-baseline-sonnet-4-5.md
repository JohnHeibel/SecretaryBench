## How to use this

Part A is every failing op. For each one, read the email, the key, and what the model had, then tick one code and write a line of notes. Do not look at the grader's reason until you have formed your own view; it is there so the two can be compared afterwards.

| code | meaning |
|---|---|
| **MODEL** | the answer key is right and the model did not do it, or did it wrong (missing, wrong day, wrong kind, duplicate, stale copy, not cancelled) |
| **KEY** | the answer key is wrong or the email does not support it: wrong date, wrong kind, no cue in the prose, an obligation nobody would infer |
| **PLAN** | the email was served after the date it talks about, so no answer could be right (register K-1) |
| **GRADER** | the model did the right thing and the grader still failed it |
| **AMBIGUOUS** | reasonable people would disagree |

Things the worksheet resolves for you: **expected dates are already computed** from the serve plan, and each anchor a key refers to is listed with its value and the earlier email that set it. **Objects** are everything on the calendar for that node on that day: ★ created for this email, ☆ created that day for a sibling email, no mark = inherited from an earlier day.
